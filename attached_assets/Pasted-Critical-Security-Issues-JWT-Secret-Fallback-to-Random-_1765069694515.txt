Critical Security Issues

JWT Secret Fallback to Random Bytes on Every Restart
File: routes/auth.js & middleware/auth.jsJavaScriptconst JWT_SECRET = process.env.JWT_SECRET || process.env.SESSION_SECRET || crypto.randomBytes(32).toString('hex');
If JWT_SECRET is missing, it generates a new random secret on every server restart.
This invalidates all existing tokens, logging out all users — but worse: if an attacker triggers a restart (e.g., via DoS), they can force token invalidation.
Fix: Fail fast if JWT_SECRET is missing. Never fallback to random.
JavaScriptif (!process.env.JWT_SECRET) {
  throw new Error('JWT_SECRET environment variable is required');
}
No Rate Limiting on Critical Endpoints
Authentication (/auth/signup, /auth/signin) has no rate limiting.
Password brute-force and account enumeration attacks are possible.
Only generic rate limiting exists in index.js, but not applied per-route or IP.
Fix: Apply strict rate limiting:
JavaScriptconst loginLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 10 });
router.post('/signin', loginLimiter, ...);
SQL Injection Risk via Direct String Concatenation (in some queries)
While most queries use parameterized $1, $2, some dynamic queries are vulnerable.
Example: In users.js search:
JavaScriptWHERE username ILIKE $1→ Safe (parameterized)
But in conflicts.js, messages.js, etc., some complex queries use template literals with user input indirectly.
Risk: Medium, but increases with future refactors.
Fix: Never interpolate user data. Always use parameterized queries.

No Email Verification on Signup
Users can sign up with any email — no confirmation required.
Enables spam/bot accounts and email spoofing.
Fix: Implement email verification flow with one-time tokens.

No Password Strength Requirements
Password is accepted with no minimum length or complexity.
bcrypt is used (good), but weak passwords are allowed.
Fix: Enforce minimum 8 chars, require letters + numbers.


High Severity Issues

CORS Misconfigured with Wildcard Origin
File: metro.config.jsJavaScriptres.setHeader('Access-Control-Allow-Origin', '*');
Allows any website to make authenticated requests using user cookies/tokens (if same-site not enforced).
Enables CSRF + XSS exploitation from malicious sites.
Fix: Set specific origin (e.g., your Expo tunnel or production domain).
JavaScriptconst allowedOrigin = process.env.EXPO_PUBLIC_API_URL || 'https://yourdomain.com';
res.setHeader('Access-Control-Allow-Origin', allowedOrigin);
No Helmet.js or Basic HTTP Security Headers
No protection against clickjacking, MIME sniffing, XSS (partially), etc.
Fix: Add helmet:
Bashnpm install helmetJavaScriptapp.use(helmet());
app.use(helmet.contentSecurityPolicy({ ... }));
File Uploads Without Validation or Virus Scanning
Profile photos and event images are uploaded directly (presumably to Replit filesystem or external service).
No MIME type validation, size limits, or virus scanning.
Risk: Malicious files (e.g., .svg with XSS, .exe renamed).
Fix: Validate MIME, limit size (<5MB), use virus scanning (e.g., ClamAV or Cloudflare).


Moderate Severity Issues

Profanity Filter Easily Bypassed
Only checks basic variations (f*ck, sh1t, etc.).
Misses creative bypasses: f.u.c.k, fu.ck, Unicode lookalikes, etc.
Fix: Use a robust library like bad-words or leo-profanity with custom list.

Location Sharing Has No Expiration or Revocation
Once enabled, users share real-time location indefinitely.
No way to stop sharing except toggling off (but no server-side timeout).
Fix: Add automatic expiration after event ends + revocation endpoint.

No Audit Logging
Critical actions (delete event, remove attendee, resolve conflict) are not logged.
Hard to trace abuse or disputes.
Fix: Log sensitive actions with user ID and timestamp.

TomTom API Key Exposed in Frontend (if used directly)
If frontend calls TomTom directly → key is exposed.
Current code proxies through backend (/api/location/static-map) → good.
But ensure no frontend code imports or uses TOMTOM_API_KEY.

No CSRF Protection (if cookies were used)
Uses JWT in Authorization header → safe from CSRF.
But if future versions use cookies → high risk.
Current design is safe.

No Input Sanitization on Messages/Notes
HTML/JS injection possible in message display.
Risk: Stored XSS if rendered with dangerouslySetInnerHTML or WebView.
Fix: Sanitize all user-generated text (e.g., DOMPurify on web).
